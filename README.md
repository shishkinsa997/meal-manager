# Техническое задание: Приложение «Менеджер еды и продуктов» (Food & Stock Manager)

## 1. Общие положения

### 1.1. Назначение и цели продукта
Приложение является персональным менеджером, предназначенным для систематизации планирования питания, управления запасами продуктов и контроля бюджета на еду. Основная цель — снизить ментальную нагрузку, связанную с бытовыми задачами «что приготовить» и «что купить», путём автоматизации расчётов и объединения данных в единую систему.

### 1.2. Ключевая ценность
Система создаёт замкнутый цикл управления, связывающий три ключевые области:
*   **Планирование (Что есть):** Календарь приёмов пищи.
*   **Ресурсы (Что есть дома):** Учёт текущих запасов (склад).
*   **Логистика и финансы (Что купить):** Формирование оптимальных списков покупок с контролем плановых и фактических расходов.

---

## 2. Описание системы и ключевые сущности

Система строится вокруг следующих взаимосвязанных сущностей:

| Сущность | Описание и атрибуты | Связи с другими сущностями |
| :--- | :--- | :--- |
| **1. Блюдо (Dish)** | Базовая единица планирования (омлет, борщ). <br> **Атрибуты:** Название, список ингредиентов (связь с **Продуктом** и количеством на 1 порцию), опционально: КБЖУ, инструкция. | Является компонентом **Плана питания**. |
| **2. Продукт (Product)** | Конкретная товарная позиция («Молоко Простоквашино 930 мл»). <br> **Атрибуты:** Название, бренд, упаковка (вес/объём), цена за упаковку, магазин, КБЖУ на 100 г/мл/шт. | Используется в **Ингредиентах** блюд, фигурирует в **Списках покупок**, учитывается на **Складе**. |
| **3. Склад (Stock)** | Текущие остатки продуктов дома. <br> **Атрибуты:** Ссылка на **Продукт**, текущее количество (в единицах продукта или в граммах/миллилитрах). | Учитывается при формировании **Списка покупок**. Обновляется после завершения **Покупок**. |
| **4. План питания (Meal Plan)** | Календарь приёмов пищи. <br> **Атрибуты:** Дата, приём пищи (завтрак/обед/ужин), **Блюдо**, количество порций, количество дней повтора (для batch cooking). | Источник данных для расчёта требуемых **Продуктов**. |
| **5. Список покупок (Shopping List)** | Оптимизированный набор продуктов для закупки. <br> **Атрибуты:** Название, период, статус (активный/завершён), список позиций (Продукт, необходимое количество, кол-во упаковок, плановая стоимость). | Формируется на основе **Плана питания** с учётом **Склада**. Привязан к **Фактическим покупкам**. |
| **6. Фактические покупки (Actual Purchases)** | Информация о совершённых покупках. <br> **Атрибуты:** Ссылка на **Список покупок**, фактические цены на продукты, общая сумма по чеку, дата покупки. | Позволяет рассчитать финансовый план/факт. Запускает процесс обновления **Склада**. |

**Логика связи сущностей:**
`Блюдо -> (входит в) План питания -> (требует) Продукты -> (с учётом) Склада -> (формирует) Список покупок -> (превращается в) Фактические покупки -> (обновляет) Склад + (даёт) Финансовый отчёт`.

## 3. Функциональные требования

### 3.1. Управление базой данных
1.  **CRUD для Блюд:** Создание, редактирование, удаление блюд с привязкой ингредиентов (Продукт + количество).
2.  **Каталог Продуктов:** Ведение базы продуктов с указанием магазинов и цен. Возможность указать "продукт по умолчанию" для частого использования.
3.  **Управление Складом:** Ручное и автоматическое (через покупки) изменение остатков продуктов.

### 3.2. Планирование питания
1.  **Календарный интерфейс:** Drag-and-drop или пошаговое добавление блюд на дни недели/месяца.
2.  **Шаблоны и повторы:** Задание блюда на несколько дней подряд с учётом batch cooking (единоразовое приготовление на несколько порций).
3.  **Учёт едоков:** Для каждого блюда в плане указывается количество порций (1, 2, N).

### 3.3. Формирование списка покупок (ключевая логика)
1.  **Авторасчёт потребности:** Система автоматически суммирует все ингредиенты из **Плана питания** на выбранный период с учётом количества порций.
2.  **Учёт остатков:** Из общей потребности вычитаются текущие остатки со **Склада**.
3.  **Оптимизация под упаковки:** Рассчитывает необходимое количество целых упаковок **Продукта**.
    *   *Логика:* `Потребность 500 мл, упаковка 930 мл -> 1 шт.`; `Потребность 1200 мл, упаковка 930 мл -> 2 шт. (1860 мл)`.
4.  **Расчёт стоимости:** Подсчёт плановой стоимости списка на основе актуальных цен из каталога.

### 3.4. Совместное использование и синхронизация
1.  **Общий доступ к списку:** Возможность поделиться ссылкой/приглашением на **Список покупок** с другим пользователем (партнёром).
2.  **Редактирование в реальном времени:** Оба пользователя видят один список и могут отмечать купленные позиции (галочки). Изменения синхронизируются.
3.  **Разграничение прав (опционально):** Владелец списка может редактировать состав, приглашённый пользователь — только отмечать купленное.

### 3.5. Финансовый учёт и аналитика
1.  **Ввод фактических данных:** После покупки возможность указать фактические цены на продукты или общую сумму чека.
2.  **План/Факт:** Автоматическое сравнение плановой и фактической стоимости списка, вывод разницы (экономия/перерасход).
3.  **Базовая аналитика:** Графики или отчёты о средних расходах за неделю/месяц, динамике перерасхода.

### 3.6. Жизненный цикл данных
1.  **Завершение покупки:** При отметке списка как "Куплен" система автоматически добавляет купленные количества продуктов на **Склад**.
2.  **Списание со склада (будущая функция):** Возможность вручную или автоматически (при отметке "Блюдо приготовлено") уменьшать остатки на складе.

## 4. Пользовательские сценарии (User Flow)

### Сценарий 1: Планирование недели и закупка
1.  **Пользователь** открывает календарь на следующую неделю.
2.  **Перетаскивает** блюда из своей библиотеки на дни и приёмы пищи, указывает «Готовить на 3 дня» и «2 порции».
3.  **Нажимает** «Сформировать список покупок», выбирает период «с Пн по Вс».
4.  **Система** рассчитывает список, учитывая остатки молока и яиц на складе, и предлагает купить 2 упаковки молока по 930 мл.
5.  **Пользователь** делится ссылкой на список с мужем.
6.  **Муж** в магазине отмечает купленные товары. Оба видят актуальный статус.
7.  После возвращения **Пользователь** вводит итоговую сумму чека. Система показывает, что планировалось 2500₽, потрачено 2700₽ (+200₽ перерасход), и обновляет остатки на складе.

### Сценарий 2: Экспресс-дозакупка
1.  **Пользователь** видит, что на ужин запланирована паста, но на складе нет сыра.
2.  **Выбирает** блюдо «Паста» в календаре и нажимает «Купить недостающее».
3.  **Система** формирует минимальный список из отсутствующих ингредиентов (сыр, 200г), учитывая упаковку.

## 5. Нефункциональные требования

1.  **Удобство интерфейса:** Минимум действий для частых операций (планирование, добавление в список). Адаптивный дизайн для мобильных устройств (основной сценарий использования в магазине).
2.  **Производительность:** Быстрое формирование списка покупок для периода в 7-30 дней.
3.  **Конфиденциальность:** Данные пользователя (списки, склад) должны быть надёжно защищены. При совместном доступе — передаваться только по защищённой ссылке.
4.  **Целостность данных:** Автоматические расчёты (склад, финансы) должны быть точными и проверяемыми.

## 6. Этапы реализации (Roadmap)

**Фаза 1 (MVP):**
*   Управление Блюдами и Продуктами.
*   Календарь планирования с учётом порций.
*   Формирование списка покупок с базовой логикой (суммирование потребности, учёт склада).
*   Локальное хранение данных (без синхронизации).

**Фаза 2 (Core):**
*   Подключение бэкенда с синхронизацией данных между устройствами.
*   Функция совместного использования и редактирования списка покупок в реальном времени.
*   Модуль финансового учёта (план/факт).
*   Автоматическое обновление склада после покупок.

**Фаза 3 (Расширение):**
*   Продвинутая аналитика расходов и пищевых привычек.
*   Автоматическое списание продуктов со склада при отметке о приготовлении.
*   Интеграция с онлайн-чеками или API магазинов для автоматического добавления продуктов и цен.
*   Система уведомлений (заканчивается молоко, пора планировать неделю).
